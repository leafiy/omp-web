# Claude Code 运行中发送消息

> 后续更新：常规网页 Follow-up 已统一为四引擎的[服务端待发送队列](./queued-message-editing.zh-CN.md)，在交付前都可撤回或取回编辑。下文保留最初原生 `priority: later` 的协议接入与验证记录，不再代表网页 Follow-up 按钮的默认实现；Steer 仍使用原生 `priority: next`。

CC 会话运行时，网页提供“引导（Steer）”和“后续消息（Follow-up）”。只有原生 CLI 声明了消息生命周期、请求 UUID 列表和队列取消能力，入口才启用；旧版不满足条件时不假装支持。

- **引导**：消息通过同一个 SDK 输入流发送，使用原生 `priority: next`。CC 在下一可接收处理点（例如工具轮次之间）将它纳入当前回合；没有可用处理点时也可能进入下一回合。不保证打断正在执行的工具。
- **底层原生后续消息（历史接入）**：使用原生 `priority: later`，由 CC 留待后续回合。这与后续引入的网页待发送队列不同；现在的网页按钮采用文首链接中明确说明的统一队列语义。
- 不使用 `priority: now`，也不先调用停止再重发来冒充 Steer。
- 本轮只接入运行中的纯文字；斜杠命令和附件仍需等运行结束。未发送成功或回执不明确时保留草稿并提示检查队列/历史，避免盲目重复发送。发送按钮防双击，成功回执不会清掉期间新输入的草稿。

## 状态与历史

每条发送使用独立原生 UUID。待处理消息显示在队列中，收到 `command_lifecycle: started` 或原生消费 UUID 列表后，才作为用户消息写入网页显示投影。相同文字的两条发送不会按文本去重。

一个 result 可能覆盖初始消息和多个 Steer；后续消息也可能开启独立回合。仅完成当前 result 对应的 UUID，仍有输入未完成时保持运行/SSE，不因旧回合结束而提前清空队列。CC 2.1.318 的实测中，即使仍有后续消息，`queued_turn_count` 也可能为零，因此不把这个计数当作完成依据。

运行中追加消息不会重置已有流式文本、工具映射或待处理权限弹窗。重连会重放能力和未处理队列；已有会话仍按精确原生 UUID 恢复。待处理队列是进程内状态，不保证跨网页服务/CLI 进程重启持久化，也不会自动重放未完成消息。

## 停止

停止同时请求中断当前工作和取消原生待处理输入。源码依赖固定的 SDK 0.3.318：其运行时支持 `interrupt({ cancelQueued: true })`，但发布类型遗漏了参数；兼容代码集中在 `lib/claude-steering.ts`，并由真实 CLI 的假服务测试验证 `cancel_queued` 回执。

已启动的回合等待对应 result，未启动且明确取消的消息依据取消回执移除；停止期间拒绝新消息。未确认清空队列、存在遗漏的未投递输入或停止超过五秒时，会关闭当前原生进程，防止“停止后又执行”；页面明确提示，下次操作重新按原生 ID 恢复，不自动补发。已经执行的工具操作不会因此撤销。原生进程关闭时会明确废弃旧 SSE 连接，下次发送前重新连接新进程，避免恢复后丢失流式输出或审批。

## 验证

- `lib/claude-code.test.mjs` 覆盖能力门控、同回合消费多个 UUID、后续回合、迟到结果、部分文本保留、审批去重、重连队列和停止回执。
- 真实 CC 2.1.318 与真实网页适配器通过本地假 Anthropic 服务验证：Steer 在当前工具回合后进入下一次合成请求；Follow-up 不进入当前回合；停止取消待处理消息且没有追加请求。
- 原生测试运行在独立网络/PID 命名空间，网络仅有 loopback，真实 HOME、配置和登录文件不可见；使用临时目录与假 API Key，没有真实模型请求或订阅消耗。
- 浏览器使用模拟 API 验证运行中按钮、排队、错误保留草稿、防双击、重连、手机布局及停止。没有升级任何 Agent。
