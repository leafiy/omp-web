# Follow-up 队列、撤回与编辑

## 四个引擎使用相同的网页 Follow-up 队列

通过网页提交的 **Follow-up** 在 Claude Code、OMP、Pi、Codex 上都支持单条“撤回”和“取回编辑”。`lib/follow-up-session.ts` 包装各引擎适配器，管理服务端待发送队列，而不是伪造原生 CLI 不存在的取消接口。

- 新消息分配 `web-follow-up:<UUID>`，在正式交给引擎前不进入原生对话。
- 等原生轮次、重试、压缩及可观测后台工作真正空闲后，按 FIFO 逐条用原生 `prompt` 交付。它是明确的网页待发送队列，**不是 Claude 原生 `priority: later` 的同义名称**。
- 服务端负责调度，关闭浏览器不会暂停仍在运行的服务。刷新／SSE 重连恢复队列快照，epoch + revision 拒绝旧进程或过期响应覆盖新队列。
- 每会话最多 32 条、每条最多 64 KiB。当前仅支持普通文字，不排队斜杠命令或图片。
- 待发送队列属于当前网页进程，**不承诺跨服务重启或 CLI 退出持久化，不会在重启后自动重放旧指令**。这与浏览器本地草稿的持久化是两回事。

## 操作与交付边界

| 状态 | 撤回 | 编辑／恢复 |
| --- | --- | --- |
| 待发送 | 删除明确的网页 UUID，保证尚未送入引擎 | 先确认移除，再把文字放回草稿；不覆盖已有草稿，不自动发送 |
| 正在交付 | 禁用；不能把已交给引擎的消息当作未发送 | 禁用，等待原生结果 |
| 已确认交付 | 队列行移除，显示在正常对话中 | 可用消息的 hover“编辑”按钮放回输入框；不是撤回历史 |
| 交付未确认 | 不报告撤回成功，也不自动重试 | “取回副本”明确警告可能已被消费，要求检查历史 |

原生轮次失败或交付结果不确定时，后续自动发送暂停；用户明确发送新的普通消息后再继续。Stop 取消尚未交付的网页 Follow-up，并沿用原引擎的中断行为。存在待发送消息时拒绝 Fork、原生导航和可能改变会话的斜杠命令，避免投递到另一上下文。

新消息与旧状态查询交错、取回与交付竞争、两条相同文字、并发点击及多个浏览器都按服务端 UUID 和交付状态判断。确认移除后先恢复草稿，再尝试刷新队列；后续读取失败不会丢掉已取回文字。输入编辑版本也参与发送确认判断：即使取回后的文字与原文相同，晚到的入队成功回执也不会清掉它；已有相同草稿不重复拼接。修改后再次发送会重新排队，不保留原来的位置。

## Steer 与原生注入队列

Steer 仍遵守原生能力，不被转换为下一轮普通消息：Claude 使用原生 UUID 取消，OMP 使用原生 queue + text 移除。Pi 的原生 RPC 只有整队列清理，不能用“清空再补回”假装实现单条取消；Codex 尚未开放网页 Steer。引擎或扩展自行注入的队列项不会获得伪造的网页 UUID，按钮按真实能力启用。

旧原生适配器中的 Claude `follow_up` / `priority: later` 仍保留供底层协议适配，但常规网页入口由上述服务端队列统一接管。

## 已发送消息与本地草稿

已发文字的“编辑”与“复制”在同一个 hover 操作区，尺寸、边框和显示时机一致。“编辑”只放回输入框，不改写已消费的原生历史；已有草稿须先确认替换。

草稿文字按会话／引擎与目录保存在浏览器 localStorage，刷新恢复；图片只保存在内存。发送被确认后才清除对应草稿，失败或等待期间的新编辑保留。

## 验证

- `lib/follow-up-session.test.mjs`：四引擎、FIFO、单条撤回、SSE 重连、并发上限、跨实例拒绝、交付竞争、旧状态查询、原生错误暂停、未知结果不重试、Stop 与批量恢复的新消息竞争。
- `scripts/check-follow-up-ui.mjs <本地隔离预览 URL>`：真实队列模块 + 编译后的 UI + 模拟原生适配器；四引擎均验证取回、撤回、草稿保护、刷新、过期快照、一次交付、完成音效、手机布局及编辑／复制 hover 一致性。不启动真实 CLI 或调用模型。
- 本机真实 Claude CLI 在空 HOME、仅 loopback 的隔离环境中执行后台子任务，并验证保留的 Follow-up 只发送一次、撤回项不进入原生历史，以及子对话读取。模型响应来自确定性本地服务，没有真实模型请求。
